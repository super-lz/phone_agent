# 实现规格目录入口

本目录保存权威实现规格。默认主实现规格是 `main-spec.md`；落地到具体项目时，可以重命名为更明确的业务规格文件。

## 定位

- 主实现规格是业务语义源，不是代码复述。
- 主实现规格应能独立指导重建业务语义等价的系统；语言、框架和代码组织可以不同，但目标、流程、边界、规则、状态变化、失败处理、关键不变量和验收结果应一致。
- 代码与 Git 历史的来源定位以根入口 `AGENTS.md` 为准，本文件只补充实现规格规则。

## 写入边界

写入主实现规格的内容，应决定业务语义等价性，例如：

- 目标、真实用户、真实问题和可感知结果。
- 核心流程、前置条件、可用边界、状态变化和外部可观察结果。
- 数据含义、权限边界、业务规则、跨边界承诺和关键不变量。
- 失败处理、验收标准、非目标、关键决策和开放问题。

不写入主实现规格的内容，通常应留在代码里，例如：

- 语言、框架、库 API、文件组织、函数拆分和模块复用。
- 呈现方式、交互机制、协议胶水、数据访问方式和任务调度方式。
- 状态变量、内部性能技巧、临时调试过程和一次性执行记录。

判断是否写入时，只问一个问题：换一种语言、框架或代码结构后，这个信息是否仍必须保持，才能得到相同业务流程、结果和边界？如果是，写入规格；如果只是当前代码如何做到，留在代码里。

## 回写规则

读代码、改代码和验收结果时，都要主动识别主实现规格是否落后。

凡根入口要求读取本文件的任务，收尾时必须输出以下三种状态之一：已自动回写、需要确认、无真实实现变动。

- 确定文档落后：如果代码中已经存在稳定有效逻辑，而主实现规格只是落后，必须自动回写主实现规格，不再额外询问。
- 不确定实现变更：如果代码里确实存在相关实现，但无法确定是否应成为长期规格，必须先询问开发者确认。
- 无真实实现变动：如果没有发现真实代码行为变化、稳定实现缺口或规格落后问题，不修改主实现规格。
- 新需求或新约束：如果当前任务引入新的目标、边界、流程、接口、验收标准或失败处理，先总结拟变更点并反问确认，再修改主实现规格。

判断“确定文档落后”必须同时满足：

- 相关逻辑位于当前有效路径，不是死代码、注释、临时分支或未接入模块。
- 可以从代码、测试、运行结果或调用关系确认真实行为。
- 该行为影响业务语义、流程、边界、接口、状态变化、失败处理、验收标准、关键不变量或关键决策。
- 没有发现同一规格点存在互相矛盾的实现、明显未完成状态或需要产品取舍的问题。

自动回写后，回复格式固定为：

```text
---
⚠️ 已自动回写到主实现规格：
⚠️ 1. <回写点>
⚠️ 2. <回写点>
```

需要确认时，回复格式固定为：

```text
---
🚨 发现可能需要回写主实现规格，但需要开发者确认：
🚨 1. <待确认点>
🚨 2. <待确认点>

请确认：直接回写，还是你修改后我再回写？
```

没有真实实现变动时，回复格式固定为：

```text
---
🔵 未发现需要回写主实现规格的真实实现变动：
🔵 1. <没有回写的原因>
```

## 拆分规则

当前先保持单一主实现规格，不拆分。

出现以下情况之一，且继续维护单文件会降低定位效率时，必须把主实现规格升级为目录化规格：

- 主规格过长，阅读一个改动点必须扫大量无关章节。
- 若干部分已经形成稳定独立系统边界。
- 不同章节变化频率明显不同，单文件维护开始互相干扰。
- 多次出现代码实现无法清晰对应到规格章节。
- 人或 agent 经常误读主次关系。

拆分时优先按系统边界拆，不按开发阶段、任务批次或实现文件拆。推荐形态是：

```text
docs/spec/<feature-or-system>/
  index.md
  <subsystem-a>.md
  <subsystem-b>.md
```

`index.md` 是 AI 查阅入口，必须保留：

- 系统目标、当前边界、关键原则和关键决策。
- 文档地图：每个子文档负责什么业务边界，不负责什么。
- 定位线索：从用户需求、流程、数据语义、状态变化、失败处理或验收标准，应先读哪个子文档。
- 关联代码入口：只写模块、目录、路由、命令或外部接口级别的定位线索，不写函数级实现细节。
- 跨文档关系：只记录会影响业务语义的依赖、顺序、约束和不变量。

子文档必须保持单一稳定边界：一个子文档只承载一个系统、功能域或流程域；如果子文档需要频繁解释“先去看别处才懂这里”，说明拆分边界需要调整。

拆分后，任何实现变更都应先通过 `index.md` 定位到最小相关子文档，再决定是否回写；禁止为了省事同时扫读或修改大量无关规格文件。

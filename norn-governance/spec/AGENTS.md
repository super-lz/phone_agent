# 主规格治理

`main-spec.md` 是项目的语义权威，保存独立于语言、框架、文件布局或单次实现版本的持久产品目的与规则。

## 主规格应包含什么

- 真实用户、问题和可观察结果；
- 已接受范围、明确非目标和延后边界；
- 核心流程、状态、规则、接口、副作用和失败行为；
- 权限、安全、隐私、可移植性和恢复不变量；
- 推进里程碑所需的验收条件和证据；
- 重建语义等价系统所需的稳定决策。

不要在规格中放入聊天记录、每日进度、任务清单、推测性愿望列表、临时实现选择或代码级走读。

## 维护规则

- 开始架构或行为工作前，完整读取主规格。
- 新需求或有意的契约变化必须先摘要并确认，才能回写和实施。
- 当前可达代码和测试已证明某项稳定行为但规格遗漏时，在同一变更中更新规格。
- 意图不明确或不同实现不一致时，请求产品决策，不得静默选择。
- 记录语义结果和取舍，不记录产生它的对话过程。
- 明确标记 `Accepted`、`Proposed`、`Experimental` 和 `Deferred` 边界。只有已接受的当前范围可以授权实现。

## 拆分规格

主规格易于浏览时，保持单一 `main-spec.md`。只有稳定的独立系统边界已经形成，且单文件明显损害理解或所有权时才拆分。

拆分结构：

```text
norn-governance/spec/
  main-spec.md
  <system-boundary>/
    index.md
    <contract>.md
```

`main-spec.md` 仍是权威产品地图，并链接所有子规格。按稳定系统边界拆分，不按团队、工单类型或开发阶段拆分。读者必须始终能从 `main-spec.md` 发现所有规范规则。

## 项目自有规格维护约定

- 判断信息是否属于规格：换一种语言、框架或代码结构后，是否仍必须保持它，才能得到相同业务流程、结果和边界。
- 自动回写还须满足根规则的授权边界，并核实相关逻辑位于当前有效路径，可由代码、测试、运行结果或调用关系确认；不得依据死代码、临时分支、未接入模块或尚有矛盾的实现回写。
- 当前保持单一 `main-spec.md`。将来拆分时，各子规格只承载一个稳定系统、功能域或流程域；反复要求读者跳转才能理解时，应重新检查边界。
- 主规格地图及必要的子域入口保留目标、边界、关键决策、文档职责、需求定位线索和影响语义的跨文档依赖。关联代码仅提供模块、目录、路由、命令或外部接口级别的入口，不复述函数实现。
